# Design: Интеграция DsTaskBot

## Context

DsTaskBot — внешний Matrix-бот (разработчик доступен, но изменения на его
стороне — отдельный процесс). Протокол бота разобран по реальным событиям
(issue schadin/harrier-project#50):

- Транспорт: `m.room.message` (`m.text`), ответы бота — `m.in_reply_to` на
  событие-команду, `m.mentions` заполнено, E2E-прозрачно (клиент работает с
  расшифрованными событиями).
- Команды: в комнате — сначала упоминание бота, затем команда
  (`@bot !list`, `@bot @user текст`), в личке — без упоминания (`!list`,
  `!add текст`, `!add @user текст`). Все команды имеют префикс `!`:
  `!help`, `!list`, `!all`, `!history`, `!close N`, `!file N`, `!verify`;
  в личке дополнительно `!add`. Устаревший синтаксис без `!` и закрытие по
  `/N` ботом не поддерживаются.
- Дополнительные возможности бота (клиент только пробрасывает текст):
  теги `#тег` в теле задачи и фильтры `!list #тег` / `!all #тег` /
  `!history #тег`, сроки в начале текста («завтра 15:00», «20.09 18:00»,
  «через 2 ч»), напоминания («… напомни за 30 мин»), вложения (ответ файлом
  на сообщение задачи) и `!file N`.
- Ответы: `list` — 2 сообщения (по секциям), `all` — 1 сообщение (обе секции
  в одном body), создание — 1 сообщение `⏳ Задача [...] ... успешно создана!`
  (без ID задачи), закрытие — 1 сообщение (паттерн уточняется при реализации).
- Стабильные якоря: sender + паттерны `📌 /N текст (@mxid)`,
  `⏳ Задача [...] для пользователя [...]` (создание) и
  `✅ Задача [...] успешно закрыта!` (закрытие). Локализованные заголовки
  ненадёжны и в логике не участвуют.

Реализация — в форке веб-клиента (`desktop/cinny`), React 18 + TS +
matrix-js-sdk + jotai. Инвариант проекта: только механизмы протокола Matrix.

## Goals / Non-Goals

**Goals:**
- Opt-in интеграция: настройки, помощники команд, карточки, вкладка «Задачи»,
  сворачивание служебных команд (Фазы 1 + 2а из issue #50).
- Изолированный, тестируемый парсер ответов бота с graceful fallback.

**Non-Goals:**
- Доработка бота (структурированный ключ `com.dstask`, state events) —
  внешняя зависимость / Фаза 3, здесь не реализуется.
- Интерактивность средствами вне протокола (кнопки в событиях и т.п.).
- Поддержка нескольких разных ботов одновременно (один MXID в настройках).

## Decisions

### 1. Изолированный модуль-парсер
Весь разбор ответов бота — в отдельном модуле (например,
`src/app/features/dstaskbot/parser.ts`) с чистыми функциями:
`(event, myUserId) → ParsedBotReply | null`. Тесты — на реальных присланных
событиях (list×2, all×1, создание, пустые заглушки).

_Почему:_ формат текстовый и может измениться; изоляция ограничивает blast
radius, fallback возвращает `null` → рендер как обычного сообщения.

### 2. Корреляция команда → ответы через `m.in_reply_to`
После отправки команды запоминаем `event_id` и ждём сообщений от бота с reply
на него: `list` — 2 сообщения, остальные команды — 1; таймаут ~15 с, дальше
показываем собранное. Ожидание — про UX (индикатор загрузки), а не про
корректность: разбор построчный и не зависит от числа сообщений.

_Почему не счётчик сообщений как контракт:_ бот может изменить гранулярность;
построчный разбор с классификацией по assignee устойчив к этому.

### 3. Классификация по assignee, не по заголовкам
Секции «Назначены мне» / «Назначены мной» определяются построчно сравнением
MXID в `(@mxid)` с MXID текущего пользователя. Пустые сообщения-заглушки
(без 📌-строк) — по исключению; в неоднозначном случае обе секции «нет
данных», исходный текст остаётся видимым.

### 4. Кнопки — чисто клиентский рендер, действия — обычными сообщениями
«Закрыть» отправляет `!close N`, кнопка «Файлы» — `!file N`, как обычные
сообщения `m.room.message` (в комнате — с упоминанием бота, в личке — без).
Номер задачи рендерится обычным текстом без `/` и без кнопки. Никаких
кастомных типов событий — инвариант протокола.

### 5. Вкладка «Задачи» как вкладка комнаты
Новая вкладка рядом с существующими представлениями комнаты. Открытие →
отправка `!all` (личка: `!list`) → рендер секций. После создания/закрытия
через наш UI — повторный запрос (компенсирует отсутствие ID в ответе на
создание).

### 5.1 Синтаксис команд — единая сборка с учётом режима
Все команды формируются одной функцией: префикс `!` для любой команды,
упоминание бота добавляется только в обычной комнате. Создание задачи: в
комнате — `@bot @исполнитель текст`, в личке — `!add текст` /
`!add @исполнитель текст`. Теги, сроки и текст напоминаний клиент не
разбирает — пробрасывает как есть. `!help`, `!history`, `!file N`, `!verify`
и `!add` доступны через шорткат `/dstask`; `!file N` дополнительно — кнопкой
на карточке и во вкладке.

### 6. Настройки — отдельная группа, jotai + localStorage
Следуем существующим паттернам настроек клиента (jotai-атомы с персистом).
Ключи: `dstaskbot.enabled*`, `dstaskbot.botMxid` (дефолт
`@dstaskbot:ds-core.ru`). Всё off по умолчанию.

### 6.1 Сворачивание служебных ответов бота
Сворачиваются короткие ответы бота без строк-задач (подтверждения создания и
закрытия, заглушки пустых секций) — предикат: ответ от бота, без `📌 /N`-строк
и не более двух непустых строк. Ответы со списками задач остаются карточками.
Свёрнутый ответ раскрывается по клику. Управляется тем же тумблером
«Сворачивать команды», применяется и в личке с ботом.

### 6.2 Служебные уведомления — компактной карточкой
Короткое однострочное уведомление бота (без списка задач, завершённое «.» или
«!») распознаётся как `notice` и рендерится компактной карточкой-уведомлением
(пример — `Задача не найдена в этой комнате.`). Многострочные ответы и
заголовки секций (завершающиеся «:») остаются обычным текстом/карточками
задач. Тот же предикат лежит в основе сворачивания служебных ответов (6.1).

### 7. Детекция лички с ботом
Комната Direct (m.direct) или комната из двух участников, один из которых —
MXID бота из настроек. Режим влияет на формирование команд (в личке — без
упоминания) и не влияет на разбор ответов (ответы в личке и комнате идентичны —
проверено примерами).

## Risks / Trade-offs

- [Бот меняет текстовый формат ответов] → изолированный парсер, тесты на
  реальных событиях, graceful fallback на обычный текст; среднесрочно —
  структурированный ключ `com.dstask` (запрос разработчику бота).
- [Отсутствие ID задачи в подтверждении создания] → карточка создания без
  действий; вкладка обновляется перезапросом; ID запрошен в `com.dstask`.
- [Гонки при нескольких командах list/all подряд] → корреляция по
  `m.in_reply_to` на конкретное событие-команду, а не по «последнему
  сообщению бота».
- [Сворачивание служебных сообщений скроет осмысленные сообщения] →
  команды сворачиваются только при полном совпадении с синтаксисом, ответы
  бота — только короткие и без списка задач; настройка отключаема.
- [Слишком короткий ответ бота будет свёрнут ошибочно] → порог в две непустые
  строки покрывает подтверждения и заглушки; содержательные ответы (справка,
  история) длиннее и остаются видимыми.

## Migration Plan

Не требуется: новая opt-in функциональность, значения настроек по умолчанию
выключены, существующее поведение не меняется.

## Open Questions

- Формат ответа бота на `!history` (история закрытых задач) — получить при
  реализации; до этого ответ рендерится как обычный текст, если не совпал с
  известными паттернами.
- Число сообщений в ответе на `!list` (2) и `!all` (1) — перепроверить на
  живом боте после смены формата команд.
- Семантика `!all` в обычной комнате (задачи всех участников комнаты?) —
  проверить при реализации.
- Формат ключа `com.dstask` — согласовать с разработчиком бота (предложение:
  `version`, `type: task_list|task_created|task_closed`, массивы
  `assigned_to_me[]` / `assigned_by_me[]`, у `task_created` — объект `task`
  с `id`).
