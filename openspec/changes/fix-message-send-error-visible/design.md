# Design: fix-message-send-error-visible

## Context

В зашифрованных комнатах сообщения иногда не попадают на сервер: matrix-js-sdk
оставляет локальный echo со статусом `NOT_SENT`, но в групповых комнатах Harrier
это никак не отображается. Индикатор статуса (`MessageStatus.tsx`) рендерится
только для Direct при `directReadReceipts === 'checkmark'` и полностью
отсутствует в групповых комнатах (успех там подтверждается маркерами прочтения).
Отправка в `RoomInput.tsx:375` — fire-and-forget без `.catch()`: причины ошибок
(E2EE: не стартует сессия с устройством, нет OTK; `M_LIMIT`; сетевые сбои)
никуда не логируются, пользователь не может повторить отправку — текст сообщения
теряется.

Подтверждение из опроса: со стабильной сетью, только E2EE-комнаты, в Direct
пользователь видел `Cross`, в группах — ничего; после перезагрузки сообщение
пропадало (сервер его не получил).

## Goals / Non-Goals

**Goals:**
- Видимость состояния отправки собственных сообщений во всех комнатах (в группах — только аномальные состояния: `Clock`/`Cross`).
- Действия «Отправить снова» и «Удалить локально» для сообщений с ошибкой.
- Обработка отклонённых промисов отправки: логирование причины + уведомление пользователя.

**Non-Goals:**
- Автоматический retry отправки при восстановлении сети.
- Индикация `Check`/`CheckTwice` в групповых комнатах (успех — через маркеры прочтения; «доставлено» невозможно по протоколу Matrix).
- Исправление корневой причины E2EE-сбоев (диагностируется по логам пункта ниже).

## Decisions

### 1. Расширение MessageStatus: индикатор в любой комнате
`MessageStatusIndicator` уже слушает `MatrixEventEvent.Status` через
`getAssociatedStatus()`. Добавляется правило:
- статусы `NOT_SENT`/`CANCELLED` → `Cross`, `SENDING`/`QUEUED`/`ENCRYPTING` → `Clock` показываются для собственных сообщений в **любой** комнате и при любых настройках маркеров прочтения;
- статусы `Check`/`CheckTwice` (read receipts) остаются только в Direct при `checkmark` (текущее условие сохраняется).

Альтернатива — отдельный компонент индикатора — отклонена: дублирование
подписки на события статуса у одного `MatrixEvent`.

### 2. Действия в контекстном меню сообщения
В `Message.tsx` добавляются два пункта меню в первую группу (над блоком
Delete/Report), по образцу `MessageDeleteItem`:
- «Resend» (`Icons.Reload`): `mx.resendEvent(mEvent, room)` с `.catch` → лог + уведомление; после успеха SDK сам переведёт событие в `SENT`, индикатор скроется (реактивно через `MatrixEventEvent.Status`);
- «Remove Locally» (`Icons.Cross`): `mx.cancelPendingEvent(mEvent)` — по SDK
  (`room.updatePendingEvent` при `CANCELLED`) событие удаляется из pending-списка
  и из таймлайна (`removeEvent`), дополнительных действий не требуется;
  пользователь может отправить сообщение заново.

Пункты показываются только для собственных сообщений (`getSender() ===
mx.getUserId()`) со статусом `NOT_SENT`/`CANCELLED`. Тексты литеральные
(в стиле существующих пунктов меню, i18n в `Message.tsx` не используется).

### 3. Обработка ошибок отправки: утилита + toast
- Утилита `sendMessageSafely`/`sendEventSafely` (в `utils/matrix.ts`): вызывает
  SDK-метод, при отклонении логирует причину (`console.error`) и публикует
  уведомление в jotai-атом `sendErrorMessageAtom` (строка причины, ограничение
  по длине).
- Новый компонент `SendErrorToast` (jotai + `Portal` из folds, auto-dismiss ~6
  секунд, кнопка закрытия) монтируется в корне приложения (рядом с
  существующими overlay-компонентами).
- Готового toast-механизма в Cinny/folds нет (проверено), поэтому вводится
  минимальный — переиспользуемый.

### 4. Точки внедрения обработки ошибок
| Место | Вызов |
|---|---|
| `RoomInput.tsx:296,375,442` | вложения, текст, стикеры |
| `MessageEditor.tsx:157` | отправка редактирования |
| `RoomTimeline.tsx:1012` | реакции |
| `Message.tsx` | resend |

## Risks / Trade-offs

- [Toast — новый UI-механизм в приложении] → минимальная реализация (jotai + Portal), без зависимостей; при появлении «родного» механизма — замена тривиальна.
- [Тексты пунктов меню без i18n] → соответствует текущему стилю `Message.tsx` (все пункты литеральные); перевод — отдельная задача.
- [`cancelPendingEvent` может бросить исключение для неподходящего статуса] → пункты меню видны только при `NOT_SENT`/`CANCELLED`, которые допустимы по SDK; вызов оборачивается в try/catch с логом.
- [E2EE-причина сбоя остаётся неизвестной] → пункт 3 даёт текст ошибки в логах и toast; после сбора фактов — отдельная задача при необходимости.
