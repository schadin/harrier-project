# Design: MCP-доступ к запущенной сессии Harrier

## Context

Задача: schadin/harrier-project#68. Нужен MCP-сервер, через который локальный
ИИ-агент управляет **уже запущенной** сессией Harrier.

Ограничения, определяющие решение:

- Живая Matrix-сессия (matrix-js-sdk: access token, ключи E2EE, синк,
  расшифрованные события) находится в вебвью форка Cinny. Rust-бэкенд Tauri её
  не видит и не может получить без второго логина и второго устройства.
- MCP-клиенты (opencode и др.) работают на той же машине и умеют Streamable
  HTTP; stdio требует запуска отдельного процесса на каждого клиента.
- В проекте действует инвариант протокола: фичи строятся только на механизмах
  Matrix. MCP — внешний транспорт к клиенту, сами операции выполняются
  существующими средствами matrix-js-sdk.
- Настройки клиента живут в вебвью (jotai + localStorage, per-user), как
  настройки DsTaskBot.

## Goals / Non-Goals

**Goals:**

- Opt-in MCP-сервер, доступный только с loopback, с bearer-токеном.
- Разграничение прав по группам тулов с проверкой в нативном слое.
- Каталог read/write-тулов и тулов DsTaskBot, динамически регистрируемых по
  настройкам.
- Подтверждение пишущих операций в UI, аудит вызовов, предсказуемые коды
  ошибок без побочных эффектов.

**Non-Goals:**

- Удалённый доступ (сеть, TLS, OAuth) — отдельная задача.
- Вторая Matrix-сессия в Rust (`matrix-sdk`) — расходится с понятием «доступ к
  запущенной сессии».
- MCP resources/prompts, работа с медиавложениями, модерация, управление
  комнатами, чтение/запись произвольных account data.
- Обход E2EE: MCP читает только то, что клиент уже расшифровал.

## Decisions

### 1. MCP-хост в Rust, транспорт Streamable HTTP

Сервер реализуется в `desktop/src-tauri/src/mcp/` на официальном Rust SDK MCP
(`rmcp` 3.x, фича `transport-streamable-http-server`); при непригодности версии
SDK — минимальный JSON-RPC поверх `axum`/`hyper`. Версия протокола пинуется и
проверяется контрактными тестами.

Замечание по совместимости: `rmcp` 3.6.0 требует Rust 1.88, при этом
`desktop/src-tauri/Cargo.toml` декларирует `rust-version = "1.61"`. При
добавлении зависимости декларацию MSRV нужно поднять до фактически требуемой
(локальный тулчейн — 1.99.1), иначе заявленное ограничение перестаёт быть
правдой. Это изменение фиксируется в задаче про зависимости и попадает в
release notes.

_Почему:_ сервер должен жить ровно пока запущено приложение, слушать только
loopback и иметь доступ к нативным возможностям (файл токена, права `0600`,
аудит). stdio-sidecar всё равно нуждался бы в канале к запущенному приложению,
то есть в том же HTTP-мосте, плюс лишний процесс и проблема «Harrier не
запущен».

Отклонено: MCP только в вебвью (вебвью не может слушать TCP), stdio-sidecar,
отдельная сессия `matrix-sdk` в Rust.

### 2. Мост Rust ↔ вебвью с correlation id

Rust при `tools/call` эмитит событие `mcp://tool-call` с
`{ callId, tool, args }`; исполнитель в вебвью выполняет вызов и отвечает
командой `mcp_tool_result(callId, ok, payload)`. В Rust — карта
`DashMap<String, oneshot::Sender<Result>>`; таймаут 30 c; при дерегистрации
исполнителя все ожидающие вызовы получают `session_unavailable`.

Один и тот же механизм используется для диалога подтверждения: исполнитель
показывает модал и ждёт решения пользователя (60 c), результат уходит в
`mcp_tool_result`. Отдельного канала не вводим.

_Почему:_ минимальная механика поверх штатных Tauri events/commands, без
сокетов и плагинов.

### 3. Права проверяются в Rust, конфиг приходит из вебвью

Вебвью при старте сессии и при каждом изменении настроек вызывает
`mcp_set_config({ enabled, port, readEnabled, writeEnabled, e2eEnabled,
confirmWrites, dstaskbotMcpEnabled, dstaskbotGroupEnabled })`. Rust хранит
эффективный конфиг в памяти и применяет его к `tools/list` и к каждому вызову
**до** моста. Вебвью — источник настроек, но не точка авторизации.

_Почему:_ гейтинг не должен зависеть от корректности обработчика в вебвью;
нативный слой — единственное место, где можно проверить права до побочных
эффектов.

### 4. Каталог тулов, имена и параметры

| Группа | Тула | Параметры |
|---|---|---|
| read | `session_info` | — |
| read | `list_rooms` | `filter?` (`all`/`unread`/`encrypted`/`dm`) |
| read | `get_room` | `room` (id, алиас или имя) |
| read | `read_timeline` | `room`, `limit?` (≤50, дефолт 20), `before?` |
| read | `list_room_members` | `room` |
| read | `get_presence` | — |
| write | `send_message` | `room`, `text`, `reply_to?` |
| write | `set_custom_status` | `text?`, `expires?` |
| dstaskbot | `dstask_list` | `room` |
| dstaskbot | `dstask_all` | `room` |
| dstaskbot | `dstask_history` | `room`, `user?` |
| dstaskbot | `dstask_list_cached` | `room` |
| dstaskbot | `dstask_add` | `room`, `text` (только личка) |
| dstaskbot | `dstask_close` | `room`, `task` (номер) |
| dstaskbot | `dstask_file` | `room`, `task` |
| dstaskbot | `dstask_verify` | `room` |

Имена — snake_case без префиксов: клиенты показывают их как есть, а группы
передаются через права, не через имя. `room` в read/write-тулах —
обязательный идентификатор, разрешение алиаса/имени выполняется в исполнителе.
Ошибка разрешения — `room_not_found`.

### 5. Подтверждение пишущих операций

Перед выполнением `send_message`, `set_custom_status` и пишущих тулов
DsTaskBot (`dstask_add`, `dstask_close`, `dstask_file`, `dstask_verify`,
живые `dstask_list`/`dstask_all`/`dstask_history`) исполнитель показывает
модальный диалог: комната, полный текст, действия «Подтвердить»/«Отклонить»,
таймаут 60 c. Настройка «Не спрашивать подтверждение» (off по умолчанию)
отключает диалог.

_Почему:_ агент действует от имени пользователя; необратимое действие требует
явного согласия. Живые dstask-тулы отправляют сообщение боту, поэтому
подчиняются тому же правилу.

### 6. E2EE-гейт

Группа `e2e` выключена по умолчанию. При выключенной группе:
`read_timeline`, `list_room_members` (для E2EE-комнат) и dstaskbot-тулы
возвращают `room_encrypted`; `list_rooms`/`get_room` отдают только метаданные и
признак `encrypted`. Расшифровка — только штатным клиентом; MCP не получает
ключей и не инициирует расшифровку сам.

### 7. DsTaskBot: отдельный тогл и динамическая регистрация

В настройках DsTaskBot появляется тогл «Доступ через MCP», off по умолчанию.
Тулы группы `dstaskbot` регистрируются только при
`dstaskbotGroupEnabled && dstaskbotMcpEnabled`. Изменение любого из флагов
перестраивает `tools/list` и рассылает `notifications/tools/list_changed`.

- Живые тулы отправляют команду существующим `sendBotCommand` (упоминание бота
  в обычной комнате, без — в личке) и ждут ответ с `m.in_reply_to` на
  отправленное событие; допустим fallback — первое сообщение бота в комнате
  после отправки с распознанным конвертом. Таймаут 15 c → `bot_no_response`.
- `dstask_list_cached` не отправляет сообщений и отдаёт последний распознанный
  список из таймлайна комнаты (атом `dsTaskBotLastTasksAtom`, при пустом
  значении — разбор загруженного таймлайна).
- `dstask_add` доступна только в личке с ботом.
- Перед отправкой проверяется присутствие бота (`isBotInRoom`); иначе
  `permission_denied` без диалога подтверждения.

### 8. Токен

32 случайных байта (base64url) при первом включении; сравнение
constant-time (`subtle`). Хранение — файл `mcp-token` в конфигурационной
директории приложения (`paths.rs`), права `0600`. Перегенерация перезаписывает
файл и инвалидирует старый токен. Токен показывается в настройках по кнопке
«Показать» с возможностью копирования.

### 9. Аудит

Кольцевой буфер на 200 записей в памяти + персист в `mcp-audit.jsonl`
(усечение до 200 строк при записи). Запись: время, тула, сводка аргументов
(текст сообщения — первые 200 символов), результат/код ошибки. Просмотр — в
настройках, кнопка «Очистить журнал». Секреты и ключи не пишутся.

### 10. Коды ошибок

| Код | Когда |
|---|---|
| `session_unavailable` | нет активной Matrix-сессии / исполнитель не зарегистрирован |
| `permission_denied` | группа прав выключена; бот не в комнате; `dstask_add` вне лички |
| `room_encrypted` | чтение E2EE-комнаты при выключенной группе `e2e` |
| `room_not_found` | комната не разрешена по id/алиасу/имени |
| `confirmation_rejected` | пользователь отклонил операцию |
| `confirmation_timeout` | нет ответа 60 c |
| `bridge_timeout` | вебвью не ответил 30 c |
| `bot_no_response` | бот не ответил 15 c |

Ошибки возвращаются как результат тулы (`isError: true`) с машиночитаемым
`code` и человекочитаемым `message`.

### 11. Настройки

Новая секция «Доступ для агента (MCP)»: master switch, порт, токен (показ,
копирование, перегенерация), группы `read`/`write`/`e2e`, «Не спрашивать
подтверждение», журнал вызовов. Плюс тогл «Доступ через MCP» в настройках
DsTaskBot. Все значения off по умолчанию; ключи i18n ru/en.

Настройки MCP — per-user (как DsTaskBot), но сервер один на приложение: при
смене аккаунта конфиг перезаписывается текущим пользователем, а исполнитель
перерегистрируется.

### 12. Тестирование

- Rust: генерация/проверка токена (constant-time, права файла), гейтинг групп,
  состав `tools/list` при всех комбинациях флагов, `list_changed`,
  таймауты моста, кольцевой аудит, парсинг порта/занятый порт.
- Вебвью (vitest): обработчики read/write на моке matrix-клиента, E2EE-гейт,
  подтверждение (accept/reject/timeout), живые dstask-тулы (корреляция по
  `m.in_reply_to`, fallback, таймаут), `dstask_add` вне лички,
  `dstask_list_cached` без отправки.
- Контрактные: `initialize`, `tools/list`, `tools/call`, `401`,
  `notifications/tools/list_changed` против реального MCP-клиента.
- Ручной e2e: opencode → список комнат → таймлайн → `dstask_list` →
  `dstask_close` с подтверждением.

## Risks / Trade-offs

- [Расширение поверхности атаки локального приложения] → loopback, bearer-токен,
  группы прав, подтверждение записи, аудит, всё off по умолчанию.
- [MCP-спецификация развивается] → пинуем версию протокола и SDK, контрактные
  тесты.
- [Вебвью может «зависнуть»] → таймауты моста и подтверждения; вызовы
  завершаются ошибкой, а не висят бесконечно.
- [Живые dstask-тулы зависят от ответа бота] → таймаут 15 c, `bot_no_response`,
  отдельная cached-тула для быстрых сценариев.
- [Корреляция ответов бота неконтрактна] → основной путь — `m.in_reply_to`,
  fallback — первое распознанное сообщение бота после отправки; оба покрыты
  тестами.
- [Аудит может содержать чувствительные данные] → только сводка аргументов,
  усечённый текст, без токенов/ключей; журнал локальный.
- [Порт занят] → ошибка в настройках, приложение не падает, switch остаётся
  включённым для смены порта.

## Migration Plan

Не требуется: новая opt-in функциональность, все настройки выключены по
умолчанию, существующее поведение клиента не меняется.

## Open Questions

- Нужен ли отдельный read-тул для кастомных статусов других участников
  (сейчас — только собственный).
- Нужны ли MCP resources для таймлайнов (сейчас сознательно вне скоупа).
- Требуется ли ограничение списка комнат allowlist'ом в дополнение к группам
  прав — решить после первых сценариев использования.
