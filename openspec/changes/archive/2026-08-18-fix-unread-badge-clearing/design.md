## Context

Бейдж непрочитанного в списке комнат, в трее и в favicon формируется из атома
`roomToUnreadAtom` (`src/app/state/room/roomToUnread.ts`). Он обновляется тремя
путями:

- `PUT` на каждое живое событие (`handleTimelineEvent`) — значение из
  `getUnreadInfo(room)`, которое читает серверный счётчик
  `room.getUnreadNotificationCount()` (в matrix-js-sdk это `notificationCounts`,
  заполняемый из `unread_notifications` в sync);
- `DELETE` при приходе собственного read receipt (`RoomEvent.Receipt`);
- `RESET` на переходах sync (инициализация, восстановление после ошибки).

`markAsRead` (`src/app/utils/notifications.ts`) отправляет receipt через
`sendReadReceipt`. Локальный счётчик `notificationCounts` SDK обновляется **только
в следующем sync** (`sync.ts:1285-1315`), а не сразу после отправки receipt.

Проблема: после прочтения комнаты `DELETE` снимает бейдж, но любое следующее
живое событие выполняет `PUT` с ещё не обновлённым серверным счётчиком —
комната снова помечается непрочитанной с устаревшим числом. Когда sync приносит
`notification_count: 0`, счётчик SDK обнуляется, но атом не пересчитывается (нет
подписки на `RoomEvent.UnreadNotifications`). Бейдж «застревает» до перезапуска,
когда `RESET` пересчитывает атом из актуального состояния sync.

## Goals / Non-Goals

**Goals:**

- Бейдж непрочитанного снимается сразу после прочтения комнаты, без перезапуска.
- Атом `roomToUnreadAtom` всегда отражает актуальное состояние непрочитанного из
  SDK (самокоррекция при изменении счётчика).
- Минимальный footprint: только `desktop/cinny`, без изменения версии SDK.

**Non-Goals:**

- Не меняем логику авто-прочтения (`document.hasFocus()`, at-bottom) — она
  работает, receipt уходят на сервер.
- Не возвращаем `m.fully_read` marker (upstream откатил PR #2587 из-за той же
  проблемы «notification not clearing»).
- Не чиним обратную проблему «phantom badges» в бриджах (upstream #2589) — другой
  сценарий.

## Decisions

### 1. Guard в `handleTimelineEvent`: не добавлять прочитанную комнату

Перед `PUT` добавляем проверку `roomHaveUnread(mx, room)`. Если пользователь уже
прочитал комнату (read receipt на последнем событии), живое событие не будет
возвращать бейдж с устаревшим счётчиком.

Альтернатива (отклонена): обнулять `notificationCounts` локально в `markAsRead`
после `sendReadReceipt`. Это ломает счёт при новых сообщениях, пришедших после
чтения (счётчик включает и их), и не чинит уже «застрявшие» записи атома.

### 2. Самокоррекция атома через `RoomEvent.UnreadNotifications`

SDK эмитит `RoomEvent.UnreadNotifications` в `Room` каждый раз, когда меняется
счётчик (`setUnreadNotificationCount`, sync, дешифровка). Клиент (MatrixClient) это
событие **не** ре-эмитит, поэтому подписка — на уровне комнат:

- в `useBindRoomToUnreadAtom` регистрируем обработчик на каждой комнате
  `mx.getRooms()`;
- новые комнаты подхватываем через `ClientEvent.Room` (сигнатура `(room) => void`);
- при `ClientEvent.DeleteRoom` удаляем запись атома и снимаем слушатель;
- обработчик пересчитывает запись комнаты по тому же предикату, что и
  `getUnreadInfos`: исключаем space/не-join/mute; если `roomHaveNotification(room)
  || roomHaveUnread(mx, room)` — `PUT getUnreadInfo(room)`, иначе `DELETE`.

Это гарантирует: как только sync принесёт обнулённый счётчик, атом сам перейдёт в
«прочитано», даже если между `DELETE` и sync пришёл «stale» `PUT` (покрывает и
`RESET`-путь).

Альтернатива (отклонена): подписка на `ClientEvent.Sync` с полным `RESET` при
каждом sync — избыточно и дорого (пересчёт всех комнат каждые ~1-3 сек).

### 3. Временный диагностический лог

Перед фиксом добавляем `console.log`-метки в `markAsRead` и в
`useBindRoomToUnreadAtom` (`PUT`/`DELETE`/`RESET` с roomId и счётчиком), чтобы на
живой сессии подтвердить последовательность: receipt ушёл → `DELETE` сработал →
пришёл «stale» `PUT`. После подтверждения лог удаляется.

## Risks / Trade-offs

- [Сервер может не присылать `unread_notifications: {}` в sync для прочитанной
  комнаты] → счётчик SDK останется устаревшим; но guard в `handleTimelineEvent`
  не даёт вернуть бейдж, а повторное чтение/`DELETE` снимает его окончательно.
- [`UnreadNotifications` эмитится в середине обработки sync, состояние
  частично обновлено] → пересчёт атома сходится на следующем изменении счётчика;
  ложных «застреваний» не возникает, возможен лишь временный неверный счёт.
- [Дополнительные пересчёты атома на каждое изменение счётчика] → операция
  дёшевая (одна комната), в худшем случае лишний re-render бейджа.

## Migration Plan

- Изменения только в `desktop/cinny` (подмодуль). Никакой миграции данных не
  требуется.
- Откат: revert коммита(ов) фикса; лог удаляется до применения фикса.

## Open Questions

- Точная последовательность событий в живой сессии подтверждается диагностическим
  логом (задача 1) — если механизм окажется иным (например, `DELETE` вообще не
  срабатывает), фикс дополнится в зависимости от результатов.
